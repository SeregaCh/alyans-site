## Why

Сайту нужен фундамент: компилируемый проект Astro и типизированная контент-модель, которая сама отклоняет некорректные данные до того, как они попадут на страницы. Без него нечего наполнять содержанием (следующий рез) и не на чем строить вёрстку по `DESIGN.md`.

## What Changes

- Инициализация проекта Astro в корне рабочей копии: Node 20.20.2, npm (`npm ci` на сервере). Строгий TypeScript (`strict: true`), ESLint flat + `typescript-eslint`, `no-floating-promises` — явный `error`.
- Сборка (`astro build`) очищает выходной каталог перед компиляцией — файлы удалённых исходников не должны продолжать раздаваться.
- Пять коллекций контента (`src/content/config.ts` + схема, Astro Content Collections): `napravleniya`, `obekty`, `dopuski`, `dokumenty`, `rekvizity`. Поля каждой — строго по ТЗ §8, без добавления своих.
- Закрытые наборы значений — перечислением (`z.enum`) в схеме: направление объекта, тип допуска. Опечатка в этих полях обязана валить сборку. Открытые поля (наименование объекта, заказчик и т.п.) — свободный текст.
- Проверка формата копируемых значений прямо в схеме (кастомный `refine`/regex, не документация): реестровый номер, ИНН, КПП, ОГРН, ОКПО, телефон, почта отклоняют неразрывный дефис (U+2011), неразрывный пробел (U+00A0), длинное и среднее тире внутри значения.
- Одна техническая страница-заглушка `[ВРЕМЕННОЕ]`, только чтобы `astro build` имел хотя бы один маршрут (Astro не собирается без единой страницы) — без содержания, без вёрстки по DESIGN.md. Требует строки в очереди ROADMAP тем же тактом при apply (правило пометки `[ВРЕМЕННОЕ]`, METHOD §4.12).
- Демонстрация в `tasks.md`: набор заведомо неверных тестовых записей (опечатка в закрытом наборе, пустое обязательное поле, неразрывный дефис в номере) роняет сборку — проверяется по факту (ненулевой код завершения / текст ошибки), не по утверждению «работает».

## Capabilities

### New Capabilities
- `astro-build-pipeline`: сборка проекта Astro — строгий TypeScript, type-aware линтер с `no-floating-promises` как error, очистка выходного каталога перед каждой компиляцией.
- `content-schema`: пять коллекций контента со схемой валидации — обязательные поля, закрытые наборы значений (enum), формат копируемых значений (запрет типографских замен), сборка падает на невалидном контенте.

### Modified Capabilities
Нет — `openspec/specs/` пуст, изменять нечего.

## Impact

Новый код в репозитории: `package.json`, `astro.config.mjs`, `tsconfig.json`, конфиг ESLint, `src/content/config.ts` и схемы пяти коллекций, одна временная страница-заглушка. Существующий код проект не трогает — репозиторий сейчас без исходников (только служебные `.md` и `openspec/`), read-only разведка не требуется.

Вне охвата этого реза: страницы по `DESIGN.md`, вёрстка, токены, логотип, nginx, DNS, деплой, перенос реального содержания (перенос — отдельный рез 2 из ROADMAP).
