## Context

Репозиторий сейчас без исходного кода — только служебные `.md` и `openspec/`. Это первый рез очереди ROADMAP: он кладёт фундамент (проект Astro + контент-схема), на котором рез 2 (перенос содержания) и рез 3 (базовый слой UI) будут строиться. Astro и стек выбраны раньше (`DECISIONS.md`, запись «Astro как генератор»); здесь — как именно устроены сборка и схема.

## Goals / Non-Goals

**Goals:**
- Проект Astro собирается одной командой на чистой копии (`npm ci` → `astro build`).
- Пять коллекций контента из ТЗ §8 описаны схемой; невалидная запись валит сборку, а не проходит тихо.
- Правило копируемых значений (`DESIGN.md` §1.1, `CONVENTIONS.md` §2) реализовано проверкой в схеме, не текстом в документации.
- Есть повторяемый, автоматический способ доказать, что схема действительно отклоняет плохие данные — не разовая ручная проверка.

**Non-Goals:**
- Страницы, вёрстка, токены, логотип по `DESIGN.md` — отдельный рез.
- Перенос настоящего содержания (направления, объекты, допуски, реквизиты) — рез 2.
- nginx, DNS, деплой — рез «Развёртывание staging».

## Decisions

### 1. Content Collections типа `data`, не `content`
Все пять коллекций — структурированные записи (поля из ТЗ §8), не документы с телом markdown. Решение: `defineCollection({ type: 'data', schema: ... })`, записи — файлы `.yaml` без frontmatter-обвязки. Отвергнут `type: 'content'` — markdown-тело никому из полей ТЗ §8 не нужно, а его наличие провоцирует со временем писать текст мимо схемы.

### 2. `rekvizity` — коллекция с ровно одной записью
Хотя в коллекции физически один файл (`rekvizity/rekvizity.yaml`), она остаётся полноценной content-коллекцией со схемой, а не отдельным JSON вне `src/content/`. Причина: единообразие — один механизм валидации на все пять сущностей, не два разных пути для «коллекций» и «синглтона».

### 3. Проверка копируемых значений — allow-list по виду значения, одна именованная функция
Денай-лист запрещённых символов бесконечен и уже неполон в первой версии (кроме U+2011 и U+00A0 есть ещё U+2010, U+2212, U+202F, U+00AD — и это не предел), а для реестровых и лицензионных номеров, где легитимны и латиница, и кириллица, денай-лист вдобавок не ловит кириллический омоглиф, подставленный в латинскую часть номера (или наоборот): и «запрещённый», и «омоглиф» — валидные буквы каждый сам по себе, отличить их можно только зная, что они не должны стоять рядом в одном слове.

Решение: одна именованная функция `copyableValueField(kind)` в `src/content/shared.ts`, но внутри — не один общий regex, а закрытый набор allow-list по виду значения (перечислить разрешённое конечно, запрещённое — нет):
- `kind: 'inn'` — ровно 10 цифр, ничего кроме цифр.
- `kind: 'kpp'` — ровно 9 цифр.
- `kind: 'ogrn'` — ровно 13 цифр.
- `kind: 'okpo'` — 8 или 10 цифр.
- `kind: 'phone'` — цифры, `+`, пробел, дефис U+002D, круглые скобки.
- `kind: 'email'` — проверка формата адреса почты (`z.string().email()`).
- `kind: 'registryNumber'` — цифры, латинские буквы, кириллические буквы, дефис U+002D, точка, косая черта, пробел; **плюс** отдельная проверка на смешение алфавитов внутри одного слова (максимальной последовательности букв без разделителей): если в одном слове есть и латинские, и кириллические буквы одновременно — значение отклоняется. Так конкретный омоглиф не нужно перечислять — ловится сам факт смешения скриптов там, где у настоящего номера один скрипт на слово (`Л014`, `П-182`, `ССК УрСиб` — каждое слово одноязычно).

Функция остаётся одной именованной точкой (`CONVENTIONS.md` §1 «Один смысл — один держатель») — поля реестрового номера, ИНН, КПП, ОГРН, ОКПО, телефона и почты во всех коллекциях подключают её с нужным `kind`, а не пишут свой regex.

### 4. Закрытые наборы — `z.enum`, не свободная строка со списком в комментарии
Направление объекта и тип допуска — `z.enum([...])` прямо в схеме коллекции.

У направления нет поля «направление» — у него есть название (свободный текст, п. 1) и идентификатор записи. Связь `obekty` → `napravleniya` строится не по названию, а по идентификатору: перечень идентификаторов направлений (`NAPRAVLENIYA_IDS = ['inzhenernye-seti', 'pokrytiya', 'monolit'] as const`) объявляется один раз в `src/content/shared.ts`; `obekty.napravlenie` — `z.enum(NAPRAVLENIYA_IDS)` — объект физически не может сослаться на несуществующее направление, это гарантирует сам тип поля. Добавление направления — правка одного места (`NAPRAVLENIYA_IDS`), а не двух параллельных перечней.

Перенос настоящего содержания коллекции `napravleniya` (название, описание, список работ) — рез 2 (Non-Goals, ROADMAP «Порядок дальше» п. 2), в этом резе коллекция может быть пустой. Инвариант, который проверяется уже сейчас и не зависит от того, есть ли реальные записи: ни один файл в `src/content/napravleniya/` не может иметь id вне `NAPRAVLENIYA_IDS` (это не ловит сама Zod-схема поля — id коллекции берётся из имени файла, а не из проверяемого поля, — нужна отдельная регрессия, задача 4.7). При нуле файлов проверка выполняется тривиально; содержательной она станет, когда рез 2 добавит реальные записи.

### 5. Очистка выходного каталога — встроенным Node, без дополнительной зависимости
Скрипт `build` в `package.json`: `node -e "fs.rmSync('dist',{recursive:true,force:true})" && astro build`. Отвергнут `rimraf` как devDependency — задача (`rm -rf` одного каталога) не оправдывает пакет; штатный `fs.rmSync` в Node 20 делает то же самое.

### 6. Доказательство «схема валит сборку» — модульные тесты схемы, а не порча реального контента
Регрессия проверяет те же Zod-схемы, что использует Astro (`src/content.config.ts` — единственный источник схем, импортируется тестом напрямую), через `vitest`: набор заведомо неверных fixture-объектов (опечатка в enum, пустое обязательное поле, неразрывный дефис в номере) обязан провалить `schema.safeParse(...)`, и сам тест обязан упасть, если однажды это перестанет быть так. `vitest` выбран как devDependency — родной для Vite/Astro, TS без отдельной транспиляции; отвергнут `node:test` (Node 20 не транспилирует TS нативно — `--experimental-strip-types` появился только в Node 22+) и отвергнута идея гонять `astro build` на специально испорченной реальной записи на постоянной основе (сломает настоящую сборку до следующей правки, не переиспользуемо как регрессия). Разовая ручная проверка `astro build` целиком на подставной плохой записи всё равно делается один раз при apply — как сквозное доказательство, что схема действительно подключена к сборке, а не только к тесту, — с фактом (вывод команды) в паспорте реза, и запись убирается сразу после.

### 7. Единственная техническая страница — `[ВРЕМЕННОЕ]`
`astro build` не соберётся без единой страницы. `src/pages/index.astro` — минимальная техническая заглушка (без вёрстки, без контента из DESIGN.md), с HTML-комментарием `<!-- [ВРЕМЕННОЕ]: снести в рез "Страницы" -->`. Пометка требует строки в очереди ROADMAP тем же тактом (METHOD §4.12) — заводится в `tasks.md` этого реза, не откладывается на потом.

## Risks / Trade-offs

- **[Risk]** Временная страница-заглушка забудется и останется в проде → **Mitigation:** строка `[ВРЕМЕННОЕ]` в ROADMAP заводится тем же тактом; страница физически заменяется в резе «Страницы» (уже следующий пункт очереди после развёртывания staging).
- **[Risk]** Allow-list для `registryNumber` (п. 3) шире необходимого — разрешает латиницу и кириллицу одновременно, потому что заранее неизвестно, у какого будущего допуска какой алфавит в номере → **Mitigation:** проверка на смешение скриптов внутри одного слова закрывает главный практический случай (омоглиф); список видов (`kind`) закрытый и именован в одном месте (п. 3), расширяется правкой одной функции, не пятью схемами.
- **[Risk]** `vitest` — новая зависимость в devDependencies → **Mitigation:** только для сборки/разработки, в проде (статических файлах) не участвует; стандартный выбор для Vite-стека, дополнительной конфигурации не требует.
- **[Risk]** `type: 'data'` без markdown-тела может не хватить, если позже понадобится длинный форматированный текст (например, абзац «о компании» с разметкой) → **Mitigation:** вне охвата ТЗ §8 для этих пяти сущностей; если понадобится — отдельное решение архитектора в профильном резе, не молчаливое расширение схемы сейчас.

## Migration Plan

Миграции данных нет — репозиторий сейчас без исходников и без живого окружения на этот код (nginx/staging подключаются отдельным резом «Развёртывание staging»). Шаги: apply создаёт файлы → `npm ci` → `astro build` и `vitest run` проходят локально на сервере → однократная проверка «плохая запись валит `astro build`» с фактом в паспорте реза → запись убрана → коммит и push. Отката инфраструктуры не требуется: откат — `git revert`/возврат к предыдущему коммиту, живых окружений это не касается.

## Open Questions

- Технически `rekvizity` — коллекция с одной записью (решение п. 2). Если на практике API работы с «коллекцией из одного файла» в Astro окажется неудобным при вёрстке (рез «Страницы»), решение может быть пересмотрено — не блокирует этот рез.
