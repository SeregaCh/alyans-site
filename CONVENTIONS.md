## 1. Код

- **Строгость типов не ослабляется:** `strict: true` в tsconfig — данность, не предмет обсуждения. `any` на границах с внешним (ответы SDK, тела HTTP, строки БД) — только через явный тип или парсинг с проверкой, не протекающий `any`.
- **Линтер type-aware** (ESLint flat + typescript-eslint), `parserOptions` покрывает все tsconfig проекта. `no-floating-promises` — явно `error`, не дефолтом пресета: на async-бэкенде незаловленный промис проваливается молча.
- **Нарушения линтера чинятся, не глушатся** `eslint-disable`; глушение — только с причиной в строке и следом в ревью.
- **Ошибки на границах — типизированные классы**, различимые `instanceof`; не общий `catch`, не разбор строки сообщения — вызывающий код различает причины программно.
- **Сигнальная конвенция размера:** файл продукта, переваливший ~800 строк, называется в отчёте такта явно («файл X дорос до N строк, заботы: …»); молча дописывать нельзя. Решение о расщеплении — архитектор или Ревизор, не исполнитель на ходу.
- **Новая забота — новый модуль:** новый механизм, протокольный путь, экранный блок оформляется новым модулем, не приростом существующего; вызывающий код только вызывает. Тестовые файлы дробятся свободно.
- **Один смысл — один держатель:** различение или защита (что видно как «разговор», защита от повторного вызова, классификация события) реализуется в одной именованной точке; остальные места её ЧИТАЮТ, не переизобретают своим условием — две независимые реализации одного смысла расходятся молча (три случая). У пары инструментов одной поверхности защита проверяется парой, не по одному.
- **Сырьё внешних ответов сохраняется целиком** (usage, вердикты, тела) — как объект, без поимённой выборки полей: завтра не хватит другого поля.

## 2. Данные

- **Закрытые vs открытые наборы:** поле, чей набор значений ТЗ перечисляет исчерпывающе — CHECK-ограничение в БД (опечатка не проходит тихо); набор примером или правдоподобно растущий — text без CHECK. Решение по каждому полю, не пакетом.
- **Избыточные индексы не заводить:** отдельный индекс по колонке не нужен там, где она уже ведущая в уникальном ограничении той же таблицы.
- **Миграции — только вперёд:** откат схемы, пересоздание, потеря данных — никогда без явного подтверждения. После наката — проверить отсутствие drift и результат в БД; перед уникальным ограничением — read-only разведка дублей. Накат по порядку окружений, перед накатом — бэкап ненулевого размера. Имена индексов/ограничений — по конвенции инструмента (иначе drift). Команды конкретного инструмента — в `CLAUDE.md` проекта. Отключение отката — явно и средством инструмента, не пропуском (у части инструментов пропуск `down` включает автоинверсию); как именно — строка в `config.yaml` проекта. Guard внутри миграции — только с инвариантом, верным в любой среде («после DROP таблицы не существует»); эталон одного дня одной среды (счёт строк) — в паспорт реза, не в тело миграции, которая переживает и среду, и день.
- **История неизменяема:** ленты, журналы, аудит — append-only; смена состояния не правит прошлое молча.
- **Ручные вставки id** (мимо генератора приложения) — только значением формата приложения, сгенерированным заранее; «на глаз» — запрещено.

## 3. Гигиена репозитория

- **Невидимые символы запрещены** в файлах канона и документах; закрытый перечень держит сторож в регрессии. В коде — только escape-последовательностями или импортом из единой точки, никогда литералом. Текст в канон переносится набором, не копированием (копипаста из служебных файлов несёт комбинирующие символы).
- **Сторож размеров служебных .md** — в регрессии: живой файл ≤500 строк и ≤40 КБ, превышение = красный прогон; перечень файлов и правило override — METHOD, раздел 4, п.3 (здесь не дублируется).
- **Сборка — в чистый выходной каталог:** `dist/` (или аналог) очищается перед компиляцией; иначе файлы удалённых исходников продолжают исполняться и счёт тестов лжёт (призрачные тесты).
- **Коммиты без трейлеров соавторства** модели; история git не приписывает авторство агенту.
- **Версии:** семвер MAJOR.MINOR.PATCH, git-теги `vX.Y.Z`, `CHANGELOG.md` на релиз.
- **Секреты — не в argv и не в вывод:** только переменные окружения; из конфигов извлекается нужное поле, не файл целиком.

## 4. Спеки (openspec)

Правила ниже проверены на устройство фактического инструмента archive (2026-09-09): норма, которую тул не исполняет, записывается как процедура, а не как пожелание.

- **Пустая дельта у чистого рефакторинга:** инструмент archive требует хотя бы одну дельту; дельта, выдуманная под потребность тула, запрещена. Рефакторинг, не меняющий ни одной капабилити, не оформляется как openspec-change — рез ведётся паспортом в `log/` (с tasks внутри); в паспорте строка «капабилити не тронуты». Непустая дельта — синкается при archive.
- **Смена смысла или заголовка требования:** `MODIFIED` роняет сценарии живой спеки, `REMOVED`+`ADDED` с тем же именем — отказ, снятие капабилити целиком — отказ; ни одно не обходится флагом. Процедура — прямая правка живой `openspec/specs/*.md` тем же резом с машинной сверкой результата множествами заголовков (Requirement/Scenario), не глазами. **Ручная правка источника истины допустима только при трёх условиях:** прямое следствие снятого или добавленного этим же резом · сверка множествами машинно · поимённо в паспорте реза. «Раз уж открыл файл» — не основание.
- **Снос или перенос капабилити:** каждое её требование получает дом поимённо — перенесено куда или снято почему; полнота выходов проверяется машинно (множества до/после), не называнием на веру. Запись `Migration:` — утверждение о содержимом другой спеки: проверяется чтением целевого файла в момент записи.
- **Purpose капабилити** дельтой не обновляется: при смене механизма Purpose правится тем же резом отдельной задачей; гейт читает спеку после archive.
- **Дом требования** — по спекам (grep по `openspec/specs/`), не по названию документа области: «прочитал документ» и «нашёл дом требования» — разные действия.
- Пропоул называет требование ТЗ и критерий «готово»; задача, трогающая существующий код, начинается с read-only разведки.
- Требование, привязанное к событию («после входа», «после сохранения»), покрывает сам путь наступления события, не только следствие.
