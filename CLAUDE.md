## DNS и почта — правила для автора, делающего выкладку

На домене `alyans-em.ru` работает **корпоративная почта компании**. Ты DNS не трогаешь; эти правила — для автора и для тебя, когда готовишь ему инструкцию.

- Добавляются только A-записи `alyans-em.ru` и `dev.alyans-em.ru`.
- Записи **MX, SPF, DKIM, TXT не изменяются и не удаляются никогда**, ни ради проверки, ни «на минуту».
- Панель DNS у автора — правки в ней делает автор. Если нужна запись — назови её точно (тип, имя, значение, TTL).
- После любой правки DNS — проверка почты отправкой и получением письма. Без неё шаг не закрыт.

## Цикл

- `/opsx:propose` → **сразу коммит и push папки `openspec/changes/<имя>`** → ревью в чате → `/opsx:apply` → проверка на `127.0.0.1:4321` → `/opsx:archive` → commit и push.
- **Apply завершён = код закоммичен и запушен.** Правки поверх — тем же тактом. Рабочая копия не живёт впереди git.
- Рефакторинг, не меняющий ни одной капабилити, не оформляется как openspec-change: рез ведётся паспортом в `log/`, дельта под потребность тула не выдумывается.
- **Стоп вместо интерпретации:** расхождение между `DESIGN.md`, ТЗ и кодом — стоп и вопрос в чат.
- **Разведка по запросу** — read-only: перечисляешь сущности и связи, приводишь куски кода, ничего не меняешь, `/opsx` не запускаешь.

## Сборка и проверка

- `npm ci` (не `npm install`), затем сборка Astro. Выходной каталог очищается перед сборкой — иначе файлы удалённых страниц продолжают раздаваться.
- Проверка — на `127.0.0.1:4321` (`npm run preview` после сборки), жёсткой перезагрузкой: кэш показывает старую сборку.
- Твой такт заканчивается push в GitHub. Promote на production — слияние PR main → prod, делает автор; прод выкладывает таймер на 45.90.32.35.
- **Выкладка staging — последний шаг каждой завершённой работы, которая меняет сайт:** `npm run deploy:staging`, затем `curl -sSI --resolve dev.alyans-em.ru:443:127.0.0.1 https://dev.alyans-em.ru/` → `200` и заголовок `X-Robots-Tag: noindex, nofollow`. Нет `200` или нет заголовка — работа не закрыта. Правило действует после переезда staging (шаг 5 `docs/runbooks/staging-na-servere-pulta.md`); до него `deploy:staging` не запускается.

## Контент и данные

- Содержание сайта живёт в файлах контента, не в вёрстке. Правка текста — правка файла контента.
- Схема коллекций обязательна: закрытые наборы значений проверяются схемой, опечатка валит сборку.
- **В копируемых значениях — только обычные символы.** Реестровые номера, ИНН, ОГРН, телефон набираются обычным дефисом и обычным пробелом; типографские замены запрещены — иначе скопированный номер не находится в реестре.
- Не публикуются никогда: банковские реквизиты, личные мобильные телефоны сотрудников, суммы договоров.
- **Проверка отсутствия запрещённого — только общими выражениями** (форма мобильного номера, 20-значного счёта, БИК, адреса почты). Сами значения — имена, фрагменты номеров, префиксы счетов, личные адреса — не пишутся ни в файлы (включая паспорта в `log/` и шаблоны `grep`), ни в вывод команд.
- **Значение YAML с двоеточием — только в кавычках.** `- Слаботочные системы: СКС` разбирается как вложенный объект, а не строка, и падает на схеме. Это ловилось в проекте дважды; при правке любого YAML значения с двоеточием, решёткой или начинающиеся с тире кавычить сразу.
- **Нет данных — нет блока.** Блок, зависящий от файла или записи контента, при их отсутствии не рендерится вовсе: ни заглушки, ни серого прямоугольника, ни кнопки в никуда. Страница обязана оставаться полноценной без него. Местозаполнитель допустим только там, где отсутствие само по себе является содержанием, и тогда он помечается `[ВРЕМЕННОЕ]` со строкой в ROADMAP тем же тактом.
